# 05 — Realtime Media

Audio, video, screen sharing and the indicators on top of them. LiveKit is the
transport.

## Why an SFU

A WebRTC mesh requires every peer to upload N-1 streams. It stops working around
five participants. The requirement is 25+, so a selective forwarding unit is not
optional.

**LiveKit is self-hosted.** Every meeting uses it, at every participant count.

## Rejected: peer-to-peer for small meetings

A hybrid — mesh at four participants or fewer, SFU above — was considered and
rejected. Recorded here so it is not proposed again without new information.

**The translation agent is always in the media path.** It subscribes to every
microphone track and publishes audio back. In a mesh it is an additional peer, so
the arithmetic inverts:

| 4-person meeting | Uploads per client |
|---|---|
| Mesh + agent | 4 streams (3 peers + the agent) |
| SFU | 1 stream |

Peer-to-peer makes the small-meeting case worse, because the thing it avoids — a
server in the media path — is something this product requires anyway.

Three further costs, any one of which would be disqualifying on its own:

- LiveKit has no peer-to-peer mode. A hybrid means a second, independent media
  stack: raw `RTCPeerConnection` mesh, our own signalling WebSocket, our own TURN.
  Every feature gets two implementations — mute, speaking detection, screen share,
  reconnection.
- That signalling WebSocket destroys the property that makes the API trivially
  scalable: it currently holds no connections at all (module 08).
- The switch at the fifth join renegotiates every peer. Video freezes, translation
  gaps, captions drop — at the moment someone arrives. Switching back on leave makes
  a meeting hovering at 4–5 participants thrash.

**Reconsider only if** translation is decoupled from the media transport — clients
streaming microphone audio to the agent over a separate channel rather than as a
room participant. That is a different architecture, not an added code path, and it
means hand-rolling jitter buffering and backpressure that LiveKit currently
provides.

## Self-hosted LiveKit

- **Multi-node from the start.** Nodes coordinate through Redis — the same Redis
  instance already carrying rate limits and agent state (module 08). A single node
  is a single point of failure for every meeting at once.
- **A room lives on one node.** Rooms distribute across nodes; a room does not
  split. This is the same shape as the agent worker limit, and it means a very
  large single meeting is bounded by one machine's egress.
- **TURN is required**, not optional. Participants behind restrictive NATs cannot
  connect without a relay. LiveKit's built-in TURN server is used rather than a
  separate coturn deployment.
- **Not a plain HTTP service.** TLS on the signalling endpoint, and a UDP port
  range open to the internet. This shapes the network configuration; see module 08.
- **Keys are ours.** The API key and secret used to sign access tokens are
  generated by us and live only on the API and agent. See below.

## Tokens

Minted by the API only, in `POST /api/meetings/:code/join` (module 04).

Grants, deliberately narrow:

- `roomJoin`, scoped to exactly one room name
- `canPublish`, `canSubscribe`, `canPublishData`
- `identity` = participant id, so a token is not transferable between people
- Short TTL; the client refreshes through the API rather than holding a long-lived
  credential

The translation agent uses a separate identity and its own token with
`canPublish` and `canSubscribe` but a hidden flag so it does not appear as a tile.

## Client wiring

The SPA uses LiveKit's React **hooks**, not its prebuilt UI. The design is already
specified in module 02; the hooks supply the data:

| Need | Hook |
|---|---|
| Roster | `useParticipants` |
| Tracks for a tile | `useTracks` |
| Speaking state | `useIsSpeaking` |
| Local device state | `useLocalParticipant` |
| Connection quality | `useConnectionQualityIndicator` |

Containers hold these calls. Presentational components receive plain props and
know nothing about LiveKit.

## Device control

- Mic and camera toggle by enabling and disabling the local track, not by
  republishing — republishing causes a visible flicker for everyone else
- Device selection in pre-join, persisted to `localStorage` and reapplied on join
- Permission denial is a first-class state, not an error toast: the pre-join
  screen explains which permission is missing and how to grant it
- A user who joins muted stays muted; the UI never silently unmutes anyone

## Indicators

**Muted.** The mic-off icon appears top-right of the tile. Red is used, but the
icon shape changes too — colour is never the only signal.

**Speaking.** `SpeakingBars` animate and the tile gets the blue ring.
LiveKit's speaker detection provides the signal; the client does not run its own
audio analysis for this.

**Connection.** Amber only, and only for degraded quality. Good connections show
nothing — a permanent green indicator trains people to ignore indicators.

## Screen sharing

`getDisplayMedia`, published as a separate track with a screen-share source so
clients can distinguish it from camera video. When present it takes the large grid
slot and demotes participants to a strip.

Only one screen share at a time in v1. A second request replaces the first, with a
confirmation.

Audio capture from the shared tab is out of scope for v1 — it interacts badly with
the translation pipeline, which assumes microphone tracks are the floor.

## Scaling to 25+

- **Simulcast on** for camera tracks
- Small tiles subscribe to the low layer, the large tile to high
- At most 9 tiles rendered; the rest become an overflow count
- The active speaker is never paginated off screen
- **Selective subscription** for translation audio: a client subscribes to exactly
  one translated track and explicitly unsubscribes the others. Without this,
  twenty-five clients pull every language channel and the bandwidth saving of the
  channel model is lost. See module 06.
- On self-hosted infrastructure these are not merely client optimisations — they
  are the difference between a node carrying ten rooms and carrying two. Egress is
  the constraint, and it is ours to pay for now.

## Reconnection

LiveKit handles ICE restarts. What this project must handle:

- Show a reconnecting state rather than an empty grid
- Re-apply mute and camera state after reconnect, from local state not from
  whatever the server last saw
- Re-subscribe to the correct translation channel
- If the token expired during the outage, refresh it through the API and rejoin
  silently

Reconnection is where meeting apps feel broken, and it is not visible in a happy-path
demo. It gets an explicit test.

## Tests

- Token grants: a token minted for room A cannot join room B — trust boundary
- A node restart drops its rooms; clients reconnect and land on a healthy node
- Token identity matches the participant row
- Toggling mute enables/disables rather than republishing (assert track identity
  is stable across a toggle)
- Two-browser Playwright spec: B renders A's track; A mutes, B shows the muted
  indicator; A shares a screen, B renders it in the large slot
- Reconnect spec: drop the connection, restore it, assert mute state survived

## Done when

- Two browsers see and hear each other through the SFU
- Mute, camera and screen share work and are reflected on the other side
- A nine-participant room renders without dropped frames with the perf switch off
- The reconnect test passes
