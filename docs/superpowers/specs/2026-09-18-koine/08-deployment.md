# 08 — Deployment

## Units

| Unit | Runs as | Hosting |
|---|---|---|
| `apps/web` | Static build | Any static host / CDN |
| `apps/api` | Long-lived Node process | Container |
| `apps/agent` | Long-lived Node worker | Container |
| Postgres | Managed or container | |
| Redis | Managed or container | Shared counters and agent recovery state |
| LiveKit SFU | Go binary, multi-node | **Self-hosted**, Redis-coordinated |

API and agent are separate processes because they fail differently and scale
differently: the API is request-shaped and cheap, the agent is long-running,
stateful per room and expensive. A crash in the translation pipeline must not take
the REST API down with it.

Single VPS with Docker Compose covers local and staging — API, agent, Postgres,
Redis and one LiveKit node on one box, web on a CDN.

**Production runs LiveKit on its own machines from day one.** It is the only unit
with hard real-time behaviour and heavy egress, and co-locating it with the API
means a traffic spike in one degrades the other. Splitting the agent onto its own
machine is the next step and requires no code change.

## Self-hosted LiveKit

- **Two nodes minimum.** One node is a single point of failure for every meeting
  simultaneously. Nodes coordinate through the same Redis already deployed.
- **A room lives on one node** (module 05). Rooms distribute; a room does not split.
  Capacity planning is therefore per room, not per participant in aggregate.
- **Networking** is the part that differs from every other unit:
  - TLS on the signalling endpoint
  - A UDP port range reachable from the internet — this rules out hosts that only
    expose HTTP, and it is the most common reason a self-hosted SFU appears to work
    in testing and fails for real users
  - LiveKit's built-in TURN enabled, with its own TLS port, for restrictive NATs
- **Capacity.** Egress is the constraint, not CPU. A 25-person room is roughly
  50 Mbps in and up to ~100 Mbps out before simulcast helps. Size nodes on
  bandwidth and set a rooms-per-node ceiling; measure against real traffic rather
  than trusting this estimate.
- **Keys.** The API key and secret are generated by us, live only on the API and
  agent, and never reach the browser. Rotating them invalidates live tokens, so
  rotation is a planned operation, not a routine one.
- **Upgrades** drop the rooms on the node being restarted. Drain a node before
  upgrading it; clients reconnect onto a healthy node.

## Horizontal scaling

The application scales horizontally by design. What that requires of each unit:

**API — add instances behind a load balancer.** It is stateless: sessions live in
Postgres, token minting is pure, nothing is held between requests. Because LiveKit
owns signalling there are no long-lived connections, so no sticky routing and no
inter-instance pub/sub. This is the property that makes the rest easy; protect it.
Any feature that wants to keep something in process memory between requests is a
design smell and belongs in Redis or Postgres instead.

**Agent — add worker processes.** LiveKit dispatches rooms across the pool. Scale
on languages-per-room rather than participants, and see module 06 for the failover
path and the per-room channel ceiling.

**Postgres — vertical first, then read replicas.** Write volume is joins, leaves
and messages; it will not be the bottleneck for a long time. One thing does bite
early: every API instance holds its own connection pool, so connection count grows
with instance count. Put **PgBouncer** in front before the third instance, not
after the first outage.

**LiveKit — add nodes.** They coordinate through Redis and rooms distribute
across them. A single very large meeting is still bounded by one node's egress.

**Redis — one instance is enough, and it is now load-bearing.** It holds counters,
agent recovery state *and* SFU node coordination. Losing it degrades rate limiting
and spend caps; it also breaks SFU multi-node coordination, so treat it as
infrastructure rather than a cache. Persistence off, but monitored and restarted
automatically.

### What Redis is for

Three jobs that are silently wrong when counted per process:

1. **Rate limits** (module 04). An in-memory limiter across six instances permits
   six times the intended rate, weakening the only protection on meeting codes.
2. **Per-meeting spend ceilings** (module 06). The agent fleet is multi-process;
   an atomic increment is the only correct counter.
3. **Agent channel and heartbeat state** (module 06), so a replacement worker can
   recover a room.
4. **LiveKit node coordination** — which node holds which room. Owned by LiveKit,
   not by us, but it shares the instance.

All three are rebuildable or expendable. Redis is not a source of truth here, and
losing it degrades the system rather than corrupting it.

### Scheduled work

Idle-meeting timeouts and retention jobs must run **once**, not once per instance.

Serialise them with a **Postgres advisory lock**: each API instance attempts
`pg_try_advisory_lock` on a well-known key before running the tick and skips if it
does not get it. No new deployable, no leader election, a handful of lines. If job
volume ever outgrows that, the upgrade is a dedicated single-replica worker —
but do not start there.

## Environments

`local`, `staging`, `production`. Each has its own LiveKit project, Google OAuth
client with its own allow-listed redirect URIs, and database.

Local development runs LiveKit in Docker rather than pointing at Cloud, so that
tests and experiments do not consume a shared quota.

## Secrets

Server-side only, never in the SPA bundle:

```
DATABASE_URL
REDIS_URL
BETTER_AUTH_SECRET
GUEST_TOKEN_SECRET          # separate from the above by design (module 03)
GOOGLE_CLIENT_ID / SECRET
LIVEKIT_URL / API_KEY / API_SECRET     # self-generated; never in the browser bundle
OPENAI_API_KEY
```

The SPA receives only the LiveKit **URL**. It never sees an API key; every token
is minted by the API (module 05).

Env vars are parsed and validated with Zod at process start. A missing or
malformed variable fails the boot loudly rather than surfacing as a confusing
runtime error an hour later.

## Observability

Three things, because three is what gets looked at:

1. **Translation latency**, measured end to end per segment and reported as a
   distribution, not an average. This is the number the product lives or dies by
   (module 06) and it must be visible in production, not only in a spike.
2. **Cost per meeting-minute**, broken down by channel. Alerts on the ceiling.
3. **Errors**, with the meeting code attached so a report can be traced.

At more than one instance, add two more:

- **Agent worker health** — rooms per worker and re-dispatch events. A worker
  quietly dying is a meeting quietly losing translation, and nobody files a ticket
  for degraded-but-working.
- **SFU node health** — rooms and participants per node, egress per node, and
  packet loss. Self-hosting means media quality is now our number to watch;
  nobody else is watching it.

Structured JSON logs. Meeting codes are logged; message bodies and audio are not.

## Cost controls

Repeated here because they are operational, not architectural:

- Translation channels created on demand, torn down when unused
- Agent leaves when the room empties
- Per-meeting spend ceiling; on breach, degrade to captions only and tell the room
- Idle meeting timeout ends the room and releases the SFU

## Data retention

Meetings, participants and chat persist with the meeting record. No audio and no
transcripts are stored in v1 — captions are broadcast and discarded. Recording is
explicitly out of scope (main spec).

A retention window and a delete path are needed before real users, since chat
contains their words. Not blocking for v1 but must not be forgotten: the lazy
version is a scheduled job deleting meetings older than N days.

## CI/CD

CI as specified in module 01. Deployment is a container build and restart per
unit. Database migrations run through Drizzle as a step before the API starts, and
they run once — not on every container boot.

Rollback is redeploying the previous image. Migrations must therefore be additive
within a release; a destructive migration needs its own deliberate plan.

## Done when

- `docker compose up` gives a working local stack including LiveKit and Redis
- Two LiveKit nodes share Redis; killing one leaves the other serving new rooms
- A participant behind a restrictive NAT connects through TURN
- Two API instances behind a proxy enforce one combined rate limit, not two
- Two API instances run the scheduled tick once per interval, not twice
- Staging is reachable with its own Google OAuth client
- Env validation fails the boot on a missing variable
- Latency and cost dashboards exist before the first real meeting
